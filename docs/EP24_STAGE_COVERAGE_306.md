# EP24 country × stage coverage (#306)

Generated by `scripts/ep24/audit_stage_coverage.py` against the shared MongoDB frame, 2026-10-27.
**Counts only** — no row content, quotes, transcripts or identifiers.

## Why this report exists

The pipeline records a status per stage, but "status says success" and "there is a result" are not the
same claim — and the gap between them is where the real defects are. This audit keeps four states
apart, and a fifth bucket for work-queue markers:

| state | meaning |
|---|---|
| **completed** | at least one contracted output column carries something |
| **not started** | no output and no status |
| **failed** | the stage's own status says so |
| **claimed but empty** | the status says success, every output column is empty |
| **other** | `REPROCESS` / `DELETE` markers — honest non-results, neither failure nor success |

`claimed but empty` is invisible in any denominator built on `status = ok`, which is exactly why it
is measured separately.

A stage's status/reason/error/model columns never count as its own output — otherwise a stage would
look complete because it wrote its failure reason.

## Findings

**1. The summary stage claims success without producing anything, at scale.**
1,906 Finnish, 1,551 Polish and 693 Portuguese rows carry a success `processing_status` while every
summary output column is empty. A direct check on Finland confirms the mechanism rather than the
metric: **1,906 rows have `processing_status = OK`, no summary text, and no `metadata` field at all**.
In the same population, 631 rows are marked `REPROCESS` and 26 `DELETE` — that is, the pipeline does
know how to flag "not done"; it simply also flags some of them `OK`.

Consequence: any coverage figure computed from `processing_status = OK` overstates the summary stage
by roughly a factor of three in Finland and by about half in Poland and Portugal.

**2. Discourse stages are not comparable across countries.** Finland reaches 20.4 / 19.0 / 17.8 %
across stages 6–8. Poland reaches 0.3 / 0 / 0 and Portugal 37.7 / 1.3 / 0. A cross-country comparison
of Laclaudian coding, DNA or SNA is currently a comparison of *different pipelines*, not of different
countries. Poland's stage 6 has ten records; its stages 7–8 have none.

**3. Identity duplication is systematic, not incidental.** 1,575 Finnish, 1,862 Polish and 986
Portuguese rows share a media key with another row. This is the `video` vs `ingest` distinction from
#205 seen from the database side: the frame stores one row per ingest run, not per video.

**4. Language mapping is clean.** The only `asr_language` values present are `fi`, `pl` and `pt`, each
confined to its own country. No cross-country leakage in this dimension.

**5. Stage 9 is not auditable from this frame.** The RDF stage contracts no output columns here and
writes to its own store. Reporting it as 0 % would have been a fabricated finding, so it is reported
as *not auditable* instead.

## What would fix it

* **Status must mean output.** A stage should not write `OK` unless at least one contracted output
  column is populated. That invariant is testable at the stage boundary and belongs there, not in a
  dashboard.
* **Rerun stages 6–8 for Poland and Portugal** before any cross-country discourse claim is published.
  This is an execution gap, not a code defect, and it is the single largest limitation on the data.
* **Deduplicate at the export boundary** (already implemented in `scripts/ep24/export_mongo_results.py`)
  and investigate *why* the same media is re-ingested: a duplicate row is cheap, a duplicated
  statement in a discourse count is not.

## Limits of this report

* One snapshot, taken 2026-10-27. No reruns were executed, so "before/after" is not claimed.
* The success/failure status vocabularies are declared in `ep24_coverage_audit.py`, not read from the
  pipeline. Values outside them land in `other` and are listed rather than guessed at.
* Counts are of *rows in the shared frame*, not of distinct videos. Read them next to the media counts.
