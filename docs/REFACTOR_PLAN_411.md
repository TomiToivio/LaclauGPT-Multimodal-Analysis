# Refactor plan for #411 — audit first, then small PRs

Issue #411 asks for a repository-wide clarity refactor, split into reviewable PRs, with no change to
methodology, datasets, CLI behaviour or exported formats. This page is the **before** half: what exists,
what duplicates what, where the readability gaps are, and the order I propose to fix them. Everything
below is derived from the tree by [`REPO_MAP.md`](REPO_MAP.md) (generated by `tools/repo_map.py`) and from
reading the modules it flags.

## The shape of the repository today

```

```

## Gaps, in the order they hurt a researcher

### 1. The three analytical stages have no docstring at all

`roihu_summary.py` (741 lines), `roihu_postprocess.py` (623) and `roihu_populism.py` (618) open with code.
These are exactly the stages where an analytical decision is made, and they are the three largest
modules in the tree without a description. The legacy Puhti modules (5, 1,332 lines together) also lack
docstrings, but they are frozen history — worth one line each saying so, nothing more.

### 2. Step 6 and Step 7 share five functions

The duplication scan finds the same normalised bodies at both call sites:

| similarity | function | step 6 | step 7 |
| ---: | --- | --- | --- |
| 1.00 | `build_prompt_context` | `roihu_populism.py:234` | `step_7_roihu_discourse_network_analysis.py:259` |
| 1.00 | `_clean_document` | `:385` | `:470` |
| 1.00 | `_resume_from_mongo` | `:446` | `:541` |
| 0.95 | `_persist_row` | `:431` | `:515` |
| 0.93 | `_prepare_context` | `:403` | `:488` |
| 0.84 | `process_country` | `:478` (125 lines) | `:659` |

Two coding stages that are supposed to differ in *what they code* share their plumbing character for
character. That is a maintenance hazard with an analytical consequence: a fix applied to one copy — a
context-hash change, a resume rule — silently leaves the other stage behaving differently, and the two
stages' outputs are then compared as if they had been produced the same way.

### 3. There are two logging modules, and the difference is not stated

`ep24_logging.py` (204 lines) and `ep24_logs.py` (163) both open with the same claim: *"One log directory,
one filename convention, for every EP24 pipeline step (#324)"*. Their usage differs — **nine** modules
import `ep24_logging` (every stage plus `ep24_result_reporting`), and **one** imports `ep24_logs`
(`ep24_stage_orchestrator`). So this may be two *layers* (a stage log and an orchestrator log) sharing one
docstring, or two implementations of one convention. Either way the docstring is wrong for at least one
of them, and a reader cannot tell which file holds "the log for Poland step 2".

### 4. Three cleaning modules, all from the same issue

`ep24_cleaner.py` (526), `ep24_legacy_clean.py` (646), `roihu_clean.py` (1,100) all describe issue #35's
non-destructive cleaning. Their scopes may genuinely differ (legacy frame vs Roihu frame vs exporter);
the audit did not establish that they do, and I did not delete anything on a guess.

### 5. Two Mongo exporters

`ep24_mongo_export.py` (845) and `ep24_mongo_dashboard_export.py` (487) both describe themselves as a
read-only EP24 FI/PL/PT export from the shared database (#306, deliverables 1 and 2). Whether the second
is a projection of the first, or a second reader with its own join rules, decides whether they merge.

### 6. Prompts are not centralised, so they cannot be catalogued

The scan finds module-level prompt constants in only three places (`puhti_populism.py`,
`roihu_populism.py`, `step_7_roihu_discourse_network_analysis.py`). The summary and postprocess stages
assemble their instructions inline. #411 asks for a prompt catalogue with versions; it cannot be
generated until the prompt text has a home, and moving it is a code change with a real risk of altering
what the model sees.

### 7. Operator scripts that shadow a pipeline module

34 shell/audit scripts sit under `scripts/`. Some are one-off audits (`audit_*.py`), some are operational
(`bootstrap_ep24_mongodb.py`). Two pairs are near-identical (`apostrophe_hygiene.py` /
`cyrillic_hygiene.py` share `_iter_labels` and `_candidate_files` exactly). They are not part of the
pipeline, but they are what an operator actually runs, so they belong in the map and in the plan.

## The plan, smallest first

Each item is one PR, and each states what it does **not** change. Nothing here alters prompts, codebooks,
thresholds, stage order or output columns; anything that would is listed separately at the end as a
proposal awaiting your decision.

| # | PR | size | why first |
| ---: | --- | --- | --- |
| 1 | **This audit** — generated map, researcher guide, this plan, and a test that fails when the map goes stale | docs + one tool + one test | makes every later PR reviewable against a map instead of against memory |
| 2 | Docstrings for the three analytical stages, written from `ep24_stage_contract.py` and the prompts already in those files | 3 files, comments only | the highest readability gain with zero behavioural risk |
| 3 | State the actual division between `ep24_logging` (9 importers) and `ep24_logs` (1 importer), or merge them if there is none; either way the docstring stops claiming both are the convention | 1–2 files | an operator looking for a log currently has no way to know which file wrote it |
| 4 | Extract the five shared Step 6/7 helpers into `ep24_stage_runner.py`, with both stages importing it and their existing tests unchanged | 3 files | removes the drift risk in the two coding stages; tests prove behaviour is identical |
| 5 | Decide `ep24_cleaner` / `ep24_legacy_clean` / `roihu_clean` scopes **by reading their callers**, then merge or document each boundary | analysis + 0–2 files | the audit could not settle this, and merging on a guess would be the kind of change that looks tidy and breaks a paper |
| 6 | Same for the two Mongo exporters: if the dashboard export is a projection, call it that and share the query | 1–2 files | one join contract instead of two |
| 7 | Move prompt constants into `prompts/` with a version per prompt, keeping the rendered text byte-identical (a test compares rendered output before and after) | 3–5 files | this is the precondition for the prompt catalogue #411 asks for |
| 8 | Generate `docs/PROMPT_CATALOGUE.md` from `prompts/` + `ep24_stage_contract.py` | docs + tool | after 7, the catalogue is a view of the code rather than a second copy of it |
| 9 | Per-stage "what it decides / what it may abstain on / what it cannot see" pages for stages 1–6, one page each | docs | the researcher guide is one page; six stages deserve their own detail |
| 10 | Archive pass: the five Puhti modules and the superseded audit scripts, moved under `legacy/` with a pointer, after checking every sbatch, doc and cron entry | move + docs | last, because a move is cheap and a mistaken move is expensive |

## Behaviour verification for every code PR

- `pytest` (157 test files today) plus the stage-specific tests named in the PR.
- For anything touching a stage's output: a bounded run over the same rows before and after, compared
  column by column, in the PR description. If a column changes, say why or do not merge it.
- `python tools/repo_map.py --check` must pass, so the map cannot drift from the tree.

## Proposals that are *not* this refactor

These change what the instrument produces and therefore need your decision, separately from #411:

1. **The prompt rewrites in §5 of the issue.** Restructuring a prompt changes the model's input; it must
   land with a before/after on a fixed sample, not as part of a clarity pass.
2. **The three unproduced analytical fields.** (`laclau_*` abstention is recorded, but the corpus has
   columns no stage fills; the sibling repository tracks the same defect under #450/#452/#453.) Whether
   to fill them or retire them is a vocabulary decision.
3. **Legacy Puhti modules.** Removing them is possible; the README says the `legacy` branch already
   preserves the historical code, so the working-tree copies are redundant *if* nothing in `main`
   imports them. That needs a check per module, not a sweep.
